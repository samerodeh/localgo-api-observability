LocalGo API Testing & Observability

A small-scale evaluation of the LocalGo driver order feed, combining functional API checks, request timing, and metrics visualization.

Overview Architecture Results Troubleshooting

Project overview

The project evaluated a LocalGo test backend connected to a dedicated Supabase test project. JMeter exercised the authenticated driver feed, Postman CLI checked endpoint behavior, Prometheus collected JMeter response-time metrics, and Grafana visualized the resulting data.

Test target

Local FastAPI backend on 127.0.0.1:18083, connected to the separate LocalGo Performance Test Supabase project.

Test focus

Backend health, driver login, authenticated GET /orders/feed, and missing-token rejection.

JMeter

Load & timing

Generated login and feed requests, checked responses, and ran a small command-line test. JMeter is a desktop/CLI test runner, not a local web service; its Prometheus listener was exposed at 127.0.0.1:9270.

Postman CLI

API checks

Ran saved requests with assertions for health behavior and missing authentication. The CLI has no local service address; requests targeted the backend at http://127.0.0.1:18083.

Prometheus

Metrics storage

Web UI and query API: http://127.0.0.1:9090. Scraped the JMeter listener at 127.0.0.1:9270 every 15 seconds.

Grafana

Visualization

Troubleshooting: resolving a JMeter 404

During setup, JMeter received HTTP 404 responses because the test plan’s request configuration did not match the backend’s address and endpoint routing.

Diagnosis
Compared the JMeter sampler’s host, port, and path with the running backend configuration, then corrected the mismatched port and request settings.
Resolution
Restructured the JMeter test plan so the request components were organized and applied in the intended order, then reran the scenario and confirmed successful responses.

Outcome: The corrected run produced successful feed samples. This troubleshooting step helped distinguish a test-plan configuration problem from an API availability problem.
